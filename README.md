# RAG — Against the Machine, Will You Answer My Questions?

## Description

A Retrieval-Augmented Generation (RAG) system that answers questions about the vLLM 0.10.1 documentation. Instead of sending the whole corpus to a language model, it retrieves the most relevant chunks with BM25 and gives only those to a local Qwen model as context.

## System Architecture

```text
Indexing:   docs -> chunking -> tokenization -> BM25 index (saved to disk)
Answering:  question -> tokenization -> BM25 top-k chunks -> prompt (question + context) -> Qwen3-0.6B -> answer
```

Indexing runs once and the index is reused for every query. Retrieval and generation are separate steps, so retrieval can be tested and evaluated on its own.

## Chunking Strategy

Documents are split with LangChain text splitters:

- **Text and Markdown:** `RecursiveCharacterTextSplitter`, which splits on paragraphs, then lines, then spaces, then characters, to keep sections together.
- **Python files:** `PythonCodeTextSplitter`, which respects code structure.

The chunk size is about 1,500 characters. It is a target, not a guarantee, so real chunk lengths vary. Smaller chunks give more precise retrieval but less context; larger chunks give more context but more noise.

## Retrieval Method

Retrieval uses **BM25** through the `bm25s` library. BM25 is a lexical ranking algorithm that scores each chunk using:

- **Term frequency:** how often a query term appears in the chunk (with diminishing returns).
- **Inverse document frequency:** rarer terms count more.
- **Length normalization:** long chunks are not unfairly favored.

Chunks and queries must be tokenized the same way, so the same tokenizer and stopword setting are used at index time and query time. The top-k chunks by score are returned.

BM25 was chosen because it is lightweight, needs no embedding model, and works well for exact technical terms such as class and function names. Its weakness is that it only matches words, so a question phrased differently from the documentation can miss the right chunk.

## Answer Generation

Answers are generated by the local `Qwen/Qwen3-0.6B` model. The prompt contains the question and the retrieved chunks, and tells the model to answer only from that context and to say so when the context is insufficient. Pydantic models validate the structured inputs and outputs.

Answer quality depends on retrieval: if the relevant chunk is not retrieved, the model cannot answer correctly.

## Performance Analysis

Retrieval is evaluated with **Recall@k**:

```text
Recall@k = (expected sources found in the top-k results) / (total expected sources)
```

A retrieved chunk counts as matching an expected source when their character ranges in the same file overlap enough, measured with Intersection over Union (IoU). Matching by filename alone is not enough, because two chunks from one file can cover different parts of it.

Results on the public documentation dataset:

| Metric | Recall |
|---|---:|
| Recall@1 | 0.620 |
| Recall@3 | 0.770 |
| Recall@5 | 0.880 |
| Recall@10 | 0.890 |

Most of the gain happens within the first five results; going from 5 to 10 adds very little.

## Design Decisions

- **BM25 instead of embeddings:** simple, no vector database, strong on exact identifiers. Hybrid retrieval would be a natural next step.
- **Separate indexing from retrieval:** the index is built once and saved, so searches are fast.
- **Chunking before retrieval:** ranks focused sections and keeps the model's context small.
- **Local model:** no hosted API is needed, at the cost of hardware requirements and a small context window.
- **Pydantic and Python Fire:** Pydantic keeps data formats consistent, and Fire exposes the operations as a command-line interface.

## Challenges Faced

- **Chunk boundaries:** balancing retrieval precision against context, which is why two splitters are used.
- **Vocabulary mismatch:** BM25 ranks poorly when the question uses different words from the docs. Recall@k makes this measurable.
- **Evaluation matching:** results must be matched to reference questions and sources carefully (by question text, not only by ID), and sources compared by character range with IoU.
- **Grounded answers:** a small model can invent details, so the prompt restricts it to the retrieved context.

## Instructions

### Installation

```bash
git clone <repository-url>
cd <repository-directory>
uv sync
```

Place the vLLM 0.10.1 documentation in `data/raw/vllm-0.10.1/` (or change the configured path).

### Usage

```bash
# Build the index
uv run python -m src index

# Retrieve the top 5 chunks for a query
uv run python -m src search "AutoWeightsLoader" --k 5

# Generate an answer from the retrieved context
uv run python -m src answer "What prefixes does the AutoWeightsLoader skip in NemotronNASForCausalLM when tie_word_embeddings is True?" --k 5

# Search every question in a dataset
uv run python -m src search_dataset --dataset_path <path> --k <int> --save_directory <dir>

# Generate answers for a dataset from saved search results
uv run python -m src answer_dataset --student_search_results_path <path> --save_directory <dir>

# Evaluate retrieval
uv run python -m src evaluate \
  --student_search_result_path data/search_results/search_results.json \
  --dataset_path data/datasets/public/AnsweredQuestions/dataset_docs_public.json \
  --k 10
```
